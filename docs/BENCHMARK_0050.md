# 0050 對決 — 誰比較強

## 0. 先講結論

**以目前 repo 裡真實的回測資料判斷：0050 比較強。**

這個結論不需要新的資料就能下，因為 `data/backtests/rotation_v0.4.json` 已經有真實的五年結果：

| | 五年總報酬 | MaxDD | 贏過大盤的年數 |
|---|---:|---:|---:|
| v0.4 rotation（fixed 20/20） | +185.48% | **-59.09%** | 2 / 6 |
| TAIEX 價格指數 | +161.92% | — | — |
| TAIEX + 3.5%/年股息（0050 的合理近似） | **+211.07%** | 約 -30% | — |

三件事同時成立：

1. **含息之後策略輸了。** 185.48% < 211.07%。策略只贏「不含息的價格指數」，而價格指數不是任何人可以買的東西。
2. **風險差一個量級。** -59.09% vs 約 -30%。同樣的報酬區間，回撤是兩倍。
3. **時間分布極度不健康。** 2022、2023、2024、2025 連續四年輸給大盤，總報酬完全靠 2026 的 +180% 拉起來。

> 逐年超額：2021 +7.47%、2022 -7.70%、2023 **-38.37%**、2024 **-32.33%**、2025 **-19.18%**、2026 +126.27%

一個要贏 0050 的策略，不能只在某一年贏很多，其他年份都在流血。

## 1. 為什麼會輸：成本，不是訊號

台股買賣一趟的成本是固定的：

```
買進手續費 0.1425% + 賣出手續費 0.1425% + 證券交易稅 0.3% = 0.585%
```

這個數字會複利侵蝕本金：

| 交易次數 | 累積成本侵蝕 |
|---:|---:|
| 12 | 6.80% |
| 24 | 13.13% |
| 60 | 29.67% |
| 155 | 59.72% |
| 235 | 74.81% |
| 466 | 93.50% |

換句話說，**在五年內做 150 次交易，等於還沒開始賺就先輸掉六成的投入資金**。10 日動能在六個類股之間的排序每天都在洗牌，任何「排名變了就換股」的規則都會踩進這個陷阱。

這在本次開發過程中被實際踩到：core-satellite 的第一版沒有遲滯機制，五年做了 **466 筆交易、其中 465 筆是持有一天的來回**，把 -2.54% 的 benchmark 打成 -67.67%。這不是參數問題，是規則設計問題。

## 2. Core-satellite：為了贏 0050 而設計的架構

`coreSatellite.js`。核心想法一句話：**預設持倉就是 0050，只有真的有訊號時才偏離。**

帳戶分成 K 個 slot：

- 有合格類股時，該 slot 持有類股籃子（satellite）
- 沒有時，該 slot 持有 0050（core）

因此策略永遠 100% 在市場裡，不會像 v0.4 那樣在多頭裡空手。**完全沒有訊號時，這個策略在數學上等於 0050 買進持有** —— 測試以 1e-9 精度驗證總報酬相等、beta = 1.000、tracking error = 0。下檔因此相對 0050 有界，超額只能來自真的有訊號的時段。

### 控制 turnover 的四個機制

| 參數 | 作用 |
|---|---|
| `exitRankBuffer` | 遲滯帶：排名進入前 K 才買，要掉出 K + buffer 才賣。避免排名微幅洗牌就換股 |
| `minHoldingDays` | 最短持有天數，排名理由不能在此之前出場（停損停利不受限） |
| `rebalanceEvery` | 排名相關的換股只在再平衡日執行；風控出場仍每日判斷 |
| `cooldownDays` | 停損／停利後，該類股冷卻 N 天不得買回，消除 v0.4 出場隔天原地重進的來回費用 |

| 參數 | 作用 |
|---|---|
| `maxSatelliteSlots` | 最多幾個 slot 可以偏離 0050，直接控制 tracking error 上限 |
| `benchmarkDividendYield` | 股息同時計入 benchmark 與策略的 core 部位，任何一邊都不能靠股息假設佔便宜 |

### 衡量方式也換掉了

只看總報酬不足以宣稱「贏了 0050」。`benchmarkComparison` 產出：

- 超額報酬、beta、年化 alpha
- tracking error、information ratio
- 上漲/下跌捕獲率（up / down capture）
- **滾動一年勝率**：隨機挑一天進場，一年後贏 0050 的機率
- 最差滾動一年超額
- `costsPaid`：實際付給券商與國庫的金額，佔初始資金的比例

滾動一年勝率是最誠實的一欄。總報酬贏 0050 但滾動勝率只有 40%，代表大多數進場時點其實是輸的。

## 3. 目前還沒有真實數字

`scripts/runBenchmarkBattle.js` 已經可以完整執行：72 個 core-satellite 設定 × 4 種股息假設 ×（完整視窗 + 前後半段 + 逐年），並套用 v0.5 的 robustness gate。

但**這份報告的真實數字尚未產生**。開發環境的 network egress 只允許 GitHub，`www.twse.com.tw`、Yahoo Finance、FinMind 全部被擋，因此拿不到 0050 的真實價格。本次只用合成資料驗證程式路徑。

合成資料**不能**用來判斷策略好壞：它是帶 regime 漂移的隨機漫步，橫斷面動能在建構上就沒有真實 edge，所以合成結果既不能證明策略有用，也不能證明沒用。合成產出的報告刻意沒有 commit。

要拿到真實答案，執行 `Benchmark Battle vs 0050` workflow（或本機 `npm run battle:0050`），它會寫出 `data/backtests/benchmark_battle_0050.{json,md}`。

### 屆時該怎麼判讀

按這個順序看，任何一關沒過就是 0050 贏：

1. **含息比較**：在 3.5% 股息假設下超額是否為正？只在 0% 股息假設下贏不算贏。
2. **風險調整**：Calmar 是否高於 0050？報酬贏但回撤兩倍不算贏。
3. **滾動一年勝率**：是否顯著高於 50%？
4. **逐年分布**：是否只靠單一年份？v0.4 就是敗在這一關。
5. **Robustness gate**：鄰近參數是否也能用？（v0.5 的 family gate）

## 4. 限制

- Universe 仍是 curated 的六類股 / 十八檔，hindsight-selection 風險不變。
- 0050 使用未還原股息的收盤價，股息以年化率近似累積，不是逐筆除息還原；四種股息假設的敏感度分析就是為了界定這個近似的影響。
- 類股籃子同樣未計股息。若籃子殖利率明顯高於 0050，這裡會低估策略。
- 沒有計入滑價與流動性衝擊，只計入手續費與證交稅。
- 一段五年視窗仍然只是一個樣本。
- 研究用途，不構成投資建議。

## 附錄：第一次真實執行是錯的（2026-08-13）

第一次跑真實資料的報告**必須作廢**，原因值得記下來。

報告產出的數字是：

```
0050 五年總報酬 -23.77%，MaxDD -77.18%
72 個設定中有 61 個「贏過 0050」，判定「策略勝（含風險調整）」
```

同一段期間 TAIEX 是 **+161.92%**。一個追蹤台灣 50 指數的 ETF 不可能在指數漲 1.6 倍時虧 24% 並回撤 77%。

逐年拆開就看得出問題只在一個地方：

| 年 | 報告中的 0050 | TAIEX（真實） | 合理？ |
|---|---:|---:|---|
| 2021（部分） | +5.43% | +5.76% | ✅ |
| 2022 | -24.96% | -22.62% | ✅ |
| 2023 | +22.86% | +26.06% | ✅ |
| 2024 | +43.52% | +29.02% | ✅ |
| **2025** | **-66.67%** | **+26.85%** | ❌ |
| 2026 | +58.46% | +53.73% | ✅ |

**原因：0050 在 2025 年進行 1:4 分割，而 TWSE `STOCK_DAY` 提供的是未還原價。** 分割當天價格變成原本的 1/4，在報酬序列上就是一道 -75% 的假斷崖。反推 `(1+R) × 0.25 - 1 = -0.6667` 得 R ≈ **+33%**，才是 0050 2025 年的真實報酬。

這件事比「一個數字錯了」嚴重：

1. 所有「策略勝」的判定都是**贏一條被破壞的序列**，不是贏 0050。
2. Sweep 有一部分是在比較「哪個設定剛好在分割當天不在 core」，完全是雜訊。
3. 報告表面上完全合理 —— 有逐年表、有 IR、有滾動勝率，**每一欄都算得很認真，只是輸入是壞的**。

### 修法

`scripts/twseData.js` 新增兩層防護：

**還原（`adjustForCorporateActions`）** —— 台股有 ±10% 漲跌幅限制，因此任何收盤對收盤超過 ±11% 的變動在交易上**不可能發生**，必定是公司行為。偵測到就把該日之前的所有價格乘上比例還原成連續序列。偵測到的比例會 snap 到最接近的乾淨分割比（1:2 ~ 1:20 及其反向），前提是剩餘變動仍在漲跌幅內 —— 這樣才不會把分割當天真實的漲跌一起吃掉。減資可能是任意比例，snap 不到就用原始比例，代價是損失該日一天的報酬。

**斷路器（`assertNoUnadjustedGaps`）** —— 還原後若仍存在超過漲跌幅的單日變動，直接 throw，不讓 run 繼續。

`runBenchmarkBattle.js` 另外加一道獨立檢查：0050 五年報酬與 TAIEX 相差超過 80 個百分點就中止，並說明極可能仍有未還原的公司行為。

還原事件會列在報告開頭的表格裡，可稽核。

### 教訓

這個 repo 的整套紀律 —— champion/challenger、robustness gate、half-sample、逐年分布 —— 全部是在防「過度擬合」。但這次的失敗不是過度擬合，是**輸入資料錯了**，而所有那些 gate 對壞資料完全沒有抵抗力，反而讓錯誤看起來更可信。

因此新增一條原則：**任何 benchmark 在使用前必須先對已知的市場事實做 sanity check。** 便宜、快、而且會擋掉這一整類的錯誤。

## 附錄二：第二次執行也失敗了 —— TWSE 307（2026-08-13）

修好分割還原之後，重跑直接掛掉：

```
[EFTRI_HIST] 20260701: HTTP 307
Error: insufficient 0050 history
```

兩個獨立的問題：

**1. 沒有跟隨 redirect。** TWSE 已把 API 搬到 `/rwd/` 底下，舊路徑一律回 **307**。Node 的 `https.get` **不會**自動跟隨 redirect，所以每一個請求都被當成失敗。修法是在 `fetchJSON` 內處理 301/302/303/307/308；若 `Location` 沒帶 query 就把原本的參數接上去 —— 否則每個月份都會抓到同一批資料，而且不會有任何錯誤訊息。學到的路徑對應會記下來重用，不然剩下約 1200 次呼叫每一次都要多付一趟。

**2. 請求速率遠超 TWSE 容許值。** 真正的原因不是 spacing，是併發：抓股價用 `mapLimit(symbols, 5, ...)`，5 個 worker 各自間隔 65ms，實際速率是 **約 77 req/s**。TWSE 大約 3 req/s 就會開始拒絕。現在預設 1 個 worker、400ms 間隔（約 2.5 req/s），可用 `TWSE_CONCURRENCY` 與 `TWSE_REQUEST_SPACING_MS` 覆寫。整趟抓取約 9 分鐘。

**3. 壞資料被寫進快取。** 這是最危險的一點：抓取只成功一部分，卻仍然 `writeCache`，接著 workflow 第二步 `runRotationV05.js --offline` 會拿這份殘缺快取產出報告。現在下載完成後會先驗證每個序列的筆數，不足就**拒絕寫入快取並中止**。

三個問題都有測試涵蓋（用 local HTTP server 實測 redirect 跟隨、query 保留、memo 只付一次、redirect 迴圈中止、throttle 重試）。
